Here's a stripped down example that seems to have the same issue, but doesn't show
the processor as being less than 100%.

This is the code (based on the SBCL example from the manual, but switched to use 
bordeaux threads and verify that the reader is done before returning):

(defvar *bt-buffer-queue* (bt:make-condition-variable))
(defvar *bt-buffer-lock* (bt:make-lock "buffer lock"))

(defvar *bt-buffer* (list nil))

(defun bt-reader ()
  (bt:with-lock-held (*bt-buffer-lock*)
    (loop
     (bt:condition-wait *bt-buffer-queue* *bt-buffer-lock*)
     (loop
      (unless *bt-buffer* (return))
      (let ((head (car *bt-buffer*)))
        (setf *bt-buffer* (cdr *bt-buffer*))
        (format t "reader ~A woke, read ~A~%"
          T head))))))

(defun bt-writer ()
  (bt:with-lock-held (*bt-buffer-lock*)
    (let ((el (intern
               (string (code-char
                        (+ (char-code #\A) (random 26)))))))
      (setf *bt-buffer* (cons el *bt-buffer*)))
    (bt:condition-notify *bt-buffer-queue*))
  (loop (bt:with-lock-held (*bt-buffer-lock*)
          (when (null *bt-buffer*) (return)))))


(bt:make-thread #'bt-reader)

UPDATE:

With the dispatcher in r3029 it seems to have been partially fixed, and 
it appears that only a condition-wait in the top-level (interactive) thread 
causes the problem.

So, in Lisp only mode that works, but if there are any remote calls from
the top-level it's still going to get hit, for instance remote monitors
on something like model-output or output-key if running from Lisp.
